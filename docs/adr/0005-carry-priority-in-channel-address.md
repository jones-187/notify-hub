# 优先级随消息走：服务只负责“带”，不负责“定”

调用方（监控脚本、路由器、AI）可以给每条消息标一个优先级，服务把它带到每个通道上。

## 先把和 ADR 0004 的边界说清楚

[ADR 0004](./0004-delivery-only-no-dedup.md) 写着「去重、静默窗口、抑制、告警分级都不在服务里，
由调用方负责」。本决策和它不矛盾，但**“分级”这个词下面其实混了三件事**，要分开看：

| | 谁负责 | 服务做不做 |
|---|---|---|
| **定**级别：什么情况算紧急 | 调用方 | 不做。服务不看消息内容，也不认识“额度用完就该紧急” |
| **用**级别：按级别决定发不发、发几次、隔多久 | 调用方 | 不做。抑制、静默、去重仍然不在服务里 |
| **带**级别：把级别送到通道上 | **服务** | 做。否则调用方只能在消息里表达级别，带不到通道上，等于没有 |

服务因此多存一列 `messages.priority`。这是 ADR 0004 里「不必为此保存额外状态」的一个例外，
代价是一列，换到的是**调用方不必知道各个通道内部怎么表达优先级**。

## 决定

对外只有四档：`low` / `normal` / `high` / `urgent`，默认 `normal`；也接受数字 1-5 作为别名
（1、2 当 low，3 当 normal，4 当 high，5 当 urgent）。

服务在把通道地址交给 Apprise 之前，把档位翻译成该协议认的查询参数：

| 档位 | ntfy `?priority=` | bark `?level=` |
|---|---|---|
| `low` | `low` | `passive` |
| `normal` | `default` | `active` |
| `high` | `high` | `timeSensitive` |
| `urgent` | `max` | `critical` |

## 为什么不交给 Apprise 自己翻译

试过，**Apprise 没有“每条消息一个优先级”这个能力**。2026-10-13 用真实 HTTP 请求验证：

- `Apprise.notify()` 不接受额外参数，传 `priority=...` 直接 `TypeError`。
- `notify_type`（info / success / warning / failure）对 ntfy 和 bark **只用来挑图标**：
  换成 `failure` 不会让通知变紧急，请求里也不会多出 `X-Priority` 头。
- 优先级在 Apprise 里是**通道级**的，只能写在通道地址的查询参数上。

## 被否掉的做法

- **一条通道拆成几条**（普通档一条、紧急档一条），消息按档位选通道。
  这样做服务完全不用懂通道，但配置要按“档位数 × 通道数”翻倍，而且同一台设备会重复收到。
  省下的那点代码不值这个配置负担。
- **服务里内置“通道类型”概念**。不需要：档位只是往地址上写一个查询参数，
  而地址里本来就有协议名（`ntfy://`、`bark://`），照协议名查表就够了。
- **档位只写在通道地址上、消息级不管**。路由器那四种提醒的优先级本来就不一样，
  通道级做不到。

## Consequences

- **不在表里的协议，地址原样送出**：档位不生效，但消息照发，不会因为不认识协议就不发消息。
  加新协议时在 `priority.py` 的 `_QUERY_PRIORITY` 里补一行。
- 调用方给了不认识的档位：内网接口返回 400，**不静默猜一个**（和发送时间落在过去的处理一致）。
- ntfy 的 `normal` 档不会带 `X-Priority` 头 —— 那本来就是它的默认值，不带是对的。
- 地址上原本写着的同名参数会被覆盖，以调用方给的档位为准。
