# notify-hub 规格

> 本文件的词汇以 [GLOSSARY.md](../../GLOSSARY.md) 为准。已定的决策见 [docs/adr/](../../docs/adr/)。
>
> 工单存放位置：`.scratch/notify-hub/issues/`（本地 markdown 模式，与你其它仓库的约定一致）。

## Problem Statement

我现在要发两类消息，却没有一处统一的地方。

第一类是我自己排的提醒，例如“明天 8 点提醒我交燃气费”。第二类是监控工具发现故障时的告警。我的设备有 iPhone、Android、Windows。

因为每家工具各发各的，所以有这些问题：

- 换设备要重新配一遍。
- 提醒只能在我在电脑前、且 AI 开着的时候排。
- 关掉 AI 之后，已排好的提醒发不出去。
- 从外面（不在内网）时，我排不了提醒。

## Solution

一个常驻服务，跑在我的 Windows NAS 上，用一个 Docker 容器。

它保存“带发送时间的消息”，到点通过 Apprise 发到各个通道。通道可扩展：现在有 Bark 和 ntfy，以后加通道（例如企业微信）只是往通道表插一行，不用改代码。

它有两种接入方式：

- **入口 1（对公网）**：远程 MCP。AI 在这里排提醒。需要令牌。
- **入口 2（只在内网）**：普通 HTTP 接口。监控工具和脚本在这里发消息。需要令牌。

服务只做投递。去重、静默、告警分级由监控工具负责（见 ADR 0004）。

## User Stories

1. 作为用户，我希望对 AI 说“明天 8 点提醒我交燃气费”，AI 就把这条消息排进服务，以便我不用打开任何网页。
2. 作为用户，我希望 AI 把“明天 8 点”换算成绝对的、带时区的时间（例如 `2026-10-13T08:00:00+08:00`），以便时间不含糊。
3. 作为用户，我希望服务只用 `Asia/Shanghai` 一个时区，以便我不用每条消息都考虑时区。
4. 作为用户，我希望时间落在过去时服务直接报错，以便我立刻发现 AI 算错了时间。
5. 作为用户，我希望排期的跨度没有上限，以便排一年后、十年后的事。
6. 作为用户，我希望关掉 AI、关掉电脑之后，已排的消息照样发出，以便提醒不依赖我的电脑是否开着。
7. 作为用户，我希望服务重启、NAS 重启之后未发的消息不丢，以便一次排期长期有效。
8. 作为用户，我希望马上就能发一条消息（不排期），以便临时通知。
9. 作为用户，我希望看到未发的消息列表，以便确认 AI 到底排了什么。
10. 作为用户，我希望看到最近已发的消息，以便确认消息是否真的发出去了。
11. 作为用户，我希望取消一条未发的消息，以便排错了能收回。
12. 作为用户，我希望取消或查询一个不存在的编号时得到明确的报错，以便知道是编号错了，而不是服务坏了。
13. 作为用户，我希望每条新消息都返回一个编号，以便之后能列出、能取消。
14. 作为用户，我希望一条消息能同时发到多个通道，以便 iPhone 和 Android 都收到。
15. 作为用户，我希望以后加通道（例如企业微信）时只改配置、不改代码，以便扩展通道很便宜。
16. 作为用户，我希望某条通道暂时关掉（例如手机换了），以便不用重建容器。
17. 作为用户，我希望某一个通道发送失败时，其它通道照常收到，以便不因为一个 App 出问题而丢消息。
18. 作为用户，我希望发送失败时自动重试 3 次，以便临时网络抖动不影响送达。
19. 作为用户，我希望重试只针对失败的那个通道，以便成功的通道不会收到重复消息。
20. 作为用户，我希望重试仍失败时能看到失败原因，以便排查（例如 Bark 的令牌过期）。
21. 作为监控工具，我希望用普通 HTTP 加令牌发一条消息，以便监控发现故障时立刻通知我。
22. 作为监控工具，我希望这个 HTTP 接口只在局域网可见，以便它不会被公网扫描到。
23. 作为用户，我希望对公网只开 MCP 一个端口，以便暴露面尽可能小。
24. 作为用户，我希望任何请求缺少令牌或令牌错误时返回 401，以便别人拿到地址也发不了消息。
25. 作为用户，我希望令牌从环境变量读、不写进数据库、不进 git，以便泄露风险可控。
26. 作为用户，我希望有一个健康检查地址，以便穿透或监控能判断服务是否活着。
27. 作为用户，我希望已发（含失败、已取消）消息的占用有上限（数据库文件超过 10 MB 时删最旧的历史消息），以便 NAS 上的占用可控。
28. 作为用户，我希望未发的消息永远不被删，以便长期排期不会被我自己的清理逻辑吃掉。
29. 作为用户，我希望服务把日志写到标准输出，以便用 `docker logs` 一处看全部。
30. 作为用户，我希望数据库是单个文件，以便备份就是复制一个文件。
31. 作为用户，我希望部署时只有一个容器和一个 compose 文件，以便我在 NAS 上维护成本低。
32. 作为用户，我希望穿透只映射 MCP 端口，以便我不用在穿透工具里记两套配置。
33. 作为用户，我希望服务的日志不打印令牌和消息正文全文，以便日志文件本身不成为泄密点。

## Implementation Decisions

**运行时与容器**

- Python 3.11 或更高（本机是 3.11，镜像用 3.12），一个 Docker 容器（linux/amd64）。不用 Apprise API 容器；直接在自己进程里 import Apprise 库。
- 转发层是 Apprise 的库调用，同步阻塞。所以发送放到线程池里执行，不阻塞排期循环和请求处理。

**转发层**

- 逐通道发送，记录每个通道的结果。重试只针对失败的通道（成功的不重发）。
- 失败后重试 3 次，间隔递增。重试仍失败的通道把错误写进消息记录。
- 通道配置（Apprise 的 URL，例如 `bark://{host}/{device_key}`、`ntfy://{user}:{password}@{host}:{port}/{topic}`）存在数据库的通道表里。加企业微信就是插一行，不改代码、不重建镜像。

**排期层**

- SQLite 单文件。表里存消息：编号、标题、正文、通道集合、发送时间、状态（未发 / 已发 / 失败 / 已取消）、创建时间、尝试次数、最后错误。
- 后台循环每秒检查一次到期的消息，一次最多取 50 条。
- 发送时间在库里存 UTC，对外（MCP 和 HTTP）用带时区的 RFC3339 字符串。时区固定 `Asia/Shanghai`。
- 时间落在过去 → 直接报错，不静默改成“现在发”。

**入口**

- 一个进程，两套监听：
  - **公网端口**：只挂 MCP。用官方 Python SDK 做 streamable HTTP，路径 `/mcp`。校验 bearer 令牌。
  - **内网端口**：`POST /notify`（立刻发一条）、`GET /healthz`、`GET /messages`（只读，方便排查）。除健康检查外都要令牌，因为内网不等于可信。健康检查只回一行 ok，不需要令牌，也不包含敏感信息。
- MCP 工具 4 个，英文名：`send_message`、`schedule_message`、`list_messages`、`cancel_message`。不做“修改”，改一条等于取消加新建。
- 令牌只从环境变量读。生成方式与存放位置写在部署步骤里，不入库、不进 git。
- 不做反向代理。所有路径预留前缀（例如以后 `/notify` 变成 `/api/notify`），以后加反向代理时服务不用改。

**优先级**

- 每条消息可以带一个优先级，四档：`low` / `normal` / `high` / `urgent`，默认 `normal`。
  内网 `POST /notify` 用可选字段 `priority` 传；也接受数字 1-5 作为别名。
- 不认识的档位直接报错（400），**不静默猜一个**，和发送时间的处理一致。
- 服务只负责**带**，不负责**定**：级别是调用方定的，服务不看消息内容。
  抑制、静默、去重仍然不在服务里（见 ADR 0004、ADR 0005）。
- 落地方式是把档位翻译进通道地址的查询参数，因为 Apprise 没有消息级优先级（见 ADR 0005）。
- 排期的消息把自己的档位存起来（`messages.priority`），到点发送时照用。
- MCP 的 `send_message` / `schedule_message` 暂不开放 `priority` 参数。

**保留**

- 数据库文件超过 10 MB 时，删最旧的“已发”、“已取消”和“失败”消息，降到 8 MB 以下。
- 未发的消息永不删除，所以“已发/已取消/失败”全都删完仍超过 8 MB 时，就以现状为止，不碰未发的消息。
- “失败”也算可删：它已经不是待发的消息，只是排查用的历史。通道一直坏时，靠它才能把占用降下来。
- 未发的消息永不删除。

**部署**

- 一个 `docker compose` 文件，一个数据目录挂载，两个端口映射。
- 容器重启后继续发送未发的消息（排期在库里，不在内存里）。

**预留：按通道分流（本期不做）**

现在每条消息发给所有启用中的通道。以后若要按通道分流，扩展点是纯增量的：**协议形状不用改，存储层不用改**。

- 存储层已经按消息记录通道集合（`messages.channels`），排期循环（`scheduler.tick`）已经按它投递。要改的只有入口层那两处调用点。
- 内网 `POST /notify` 增加**可选**字段 `channels: ["company"]`；MCP 的 `send_message` / `schedule_message` 增加**可选**参数。省略时行为不变（发给所有启用中的通道），所以是向后兼容的，不破坏已有调用方。
- 通道那时需要一个稳定标识：给 `channels` 表加一列 `name`，入口用它把名字解析成通道编号即可。

## Testing Decisions

好的测试只断言**外部行为**：发一个请求，然后看两件事——数据库里多了什么、假的转发层收到了什么。不断言内部函数名、SQL 文本、日志文本。

测试用的接缝（seam）：

1. **主接缝（唯一的）**：服务的 HTTP 边界。在进程内启动 ASGI 应用，用 httpx 的 ASGI 客户端打请求。MCP 工具、内网接口都在这一层测。
2. **必须注入的两个点**（不注入就无法稳定测试）：
   - **时钟**：测试把“现在”设成 `2026-10-13T07:59:59+08:00`，再推进 2 秒，断言消息被发出。不真等时间。
   - **转发层出口**：测试用一个假的转发层，记录收到了什么。绝不在测试里真的发消息到手机。

要测的行为：

- 四个 MCP 工具：立刻发、排期、列出、取消。
- 内网接口：`POST /notify`、`GET /healthz`、`GET /messages`。
- 排期循环：到点发送；进程重启后未发消息仍会发。
- 投递语义：逐通道发送；只重试失败的通道；重试 3 次后写错误。
- 清理：数据库超过 10 MB 时删最旧的已发、已取消、失败消息；未发消息不被删。
- 鉴权：无令牌、错令牌 → 401。内网端口与公网端口都要。

先例：这是新项目，仓库里还没有测试。这是第一套，用 pytest + httpx 的 ASGI 客户端 + 临时 SQLite 文件。

不测：Apprise 内部实现（那是它的事）；真实网络发送（改为部署后做一次手动端到端验证）。

## Out of Scope

- 去重、静默窗口、抑制、告警分级（ADR 0004）。
- 附件、图片、富文本。
- 多用户、权限分离。
- Web 管理界面（ADR 0001 已记录后果）。
- 反向代理。
- 使用 ntfy 服务端自带的排期（我们用不到它的 `message-delay-limit`）。
- 修改已排的消息。
- 消息模板、统计报表。
- 自建 Bark 服务端。
- 按通道分流（发给谁）：现阶段一律发给所有启用中的通道，扩展点见「预留：按通道分流」一节。
- 企业微信通道的实际接入（本期只留位置）。

## Further Notes

- 内网穿透：节点小宝。只映射公网端口。已确认有 HTTPS、带宽 2 Mbps。文字消息远用不到 2 Mbps。
- pi 侧接入：用 `pi mcp add` 配 url 加 bearer token 环境变量。pi 不支持旧式 SSE，所以端点必须是 streamable HTTP。
- 需要人工做的步骤（我会写成清单）：在 NAS 上装 Docker、配穿透、生成令牌、把 Bark 与 ntfy 的 Apprise URL 填进通道表。
- 一个部署后要实测的点：容器在 NAS 上重启后，未发的消息是否按预期补发。预期会补发，因为排期在数据库里。这条无法在本机验证，只能在 NAS 上测。
